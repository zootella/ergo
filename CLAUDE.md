# ergo

Ergo, short for ergonomic, is a small library of helper functions shipped in four languages: JavaScript, Python, Rust, and Go. Two things are true at once. The four editions are one library, with the same function names and the same behavior, proven by a single shared test suite that all four run. And each edition is a native of its own ecosystem, written, formatted, packaged, and tested the way that language does it, so an experienced engineer in that language finds nothing foreign. concept.md explains how the two fit together; read it for the full idea and where it came from, construction.md for how each of the four editions is defined, tested, and shipped, ideas.md for ideas beyond the core requirements, including the brand, ruby.md for whether to add a fifth language, tag.md for what a tag is worth against a UUID and the objections already answered, date-history.md for how software has said dates and times since early Unix, and say-time-design.md for why sayTick and sayDuration work the way they do.

## Rules

- quad-style.md is the style guide, and it governs every edition: how code is structured, named, commented, and factored, and how each rule is spelled in JavaScript, Python, Rust, and Go. Simplicity, dense comments, result objects over exceptions, guards at trust boundaries, fewer longer files. It grew from cold3's JavaScript guide, ../cold3/style.md, and it ends with how to bring a helper over from core.js without losing its words. It's imported here, so every session starts with it: @quad-style.md
- Style is not format. Formatting is each language's standard formatter, Prettier, Ruff, rustfmt, and gofmt, run on save and checked in CI; see construction.md. Names keep the same words in every edition and take each language's case, so `Size.KB` in Python and `size::KB` in Rust are right, while JavaScript stays lowercase camelCase even for constants, `Size.kb`, by choice, to avoid shouts; construction.md has the table of spellings and concept.md the note. Where a language's formatter or its case convention disagrees with quad-style.md, the language wins. Everywhere else, quad-style.md wins. The test: a mid-career engineer in each language looks at their edition, runs their regular linter, and things are fine.
- `ttd` notes belong to the user alone. Never add, reword, or remove one. See quad-style.md.
- Use the platform, and a library only for what the platform can't do, judged function by function and form by form, so JavaScript's sha256 is Web Crypto and only its hashers and BLAKE3 are noble. A runtime dependency must be a library experienced engineers in that ecosystem already trust, never a new target of scrutiny. The JavaScript edition runs completely in a browser tab and a web worker, so it never leans on Node, and its dependencies are plain JavaScript, never WebAssembly, which is harder to say is audited. Today that's @noble/hashes in JavaScript, blake3 in Python, getrandom, sha1, sha2, blake3, and unicode-normalization in Rust, and lukechampine.com/blake3 and golang.org/x/text in Go; concept.md has the standard.
- No toss and no TossError. When an edition can't continue, it fails the way its language fails: throw an Error in JavaScript, raise in Python, panic in Rust and Go. Exceptions are the last and hardest thing ergo will make easy, not the first.
- A panic means a bug, and ergo never leaves a caller unable to avoid one. Every kind of value a function refuses has a `has` that asks and never fails and a `check` that enforces, like `hasTick` and `checkTick` before `tickToIso`, so a number from outside is asked about first. One predicate per kind of value, not a checked twin of every function; concept.md has the reasoning.
- Integers have one ceiling in every edition and every vector, JavaScript's safe range of ±(2^53 − 1), so a value within it survives all four runtimes as an integer.
- The unit suite is deterministic and fast: pinned data, nothing random, tens of milliseconds. Fuzz tests draw random inputs for a set number of seconds and run only when `ERGO_FUZZ` names the seconds: the cross-edition one, about uniformity, with `ERGO_FUZZ=4 pnpm fuzz`, and the same loop in each language, about performance; README.md has the four commands.
- One test suite, four harnesses. The tests are the specification. A function's behavior is pinned once, in the shared suite, and each language's harness confirms its own implementation against it.
- The user introduces ideas one part at a time. While they're presenting, listen and acknowledge. Don't lay out the path forward until asked.

## Status

- Eight families in all four editions: the int family, `hasInt` and `checkInt`, for an integer every edition holds exactly, the Size constants and `saySize4`, the Time constants, with `sayDuration` to say a span for a person from a template like `# hours # minutes`, and its three shortcuts, `sayTimeRemaining`, `sayTimeRemainingCoarse`, and `sayTimeRace`, the tick, an integer of milliseconds since 1970 with two exact text forms, `tickToText` and `tickToIso` and their readers back, `hasTick` and `checkTick` to ask and enforce, and `sayTick` to say one for a person from a template like `Mmm D, YYYY`, with `monthNames` and `dayNames`, the Tag family, `Tag`, `hasTag`, `checkTag`, and `tagLength`, where a scripted test proves a tag from any edition validates in every edition, Data and Bin, the types every function that trades in bytes takes and answers, where Data alone speaks text, base16, base32, base62, and base64, and the Hash family, `sha1`, `sha256`, and `blake3` all at once, `Sha1`, `Sha256`, and `Blake3` hashers a piece at a time, and `hashText`, all on Data, and the fuji hashes from icarus, the tip hash and the piece hash, with `FujiHasher` fed a piece at a time, `hashFile`, `hashStream`, `hashMeasure`, `hashStripeOverlap`, and `hashProtocol`, shaped as icarus has them, reading each language's own files and streams. Bytes cross the vectors and the drivers as tagged base16, which each driver reads with Data's own reader, and as mulberry bytes, icarus's deterministic test files. The shared vectors are one json file per family in tests/, a driver per edition, the vitest suite in javascript/ drives all four and holds the fuzz test, formatters and linters pass in each, the three workflows, and the VitePress site in docs/ has a page per family. README.md says how to run everything; the vitest suite needs all four toolchains installed.
- Under git at github.com/zootella/ergo since October 15, 2026, and published that day as 0.1.0 on all four registries: @zootella/ergo on npm, zootella-ergo on PyPI and crates.io, and github.com/zootella/ergo/go tagged go/v0.1.0. 0.1.1 and 0.1.2 followed on October 18, the first releases through the pipeline end to end, with 0.1.2 adding hasTick and checkTick, and 0.1.3 on October 20 added Data and Bin, the hashes, and the fuji hashes, with ergo's first runtime dependencies. A release is one command at the root, `pnpm release patch` or `minor`, which runs release.js, which sets the version, commits, and pushes a v tag; .github/workflows/publish.yml then tests, publishes to the three registries by trusted publishing, tags the Go module, and makes the GitHub release. construction.md has the details. The site is a placeholder at zootella.github.io/ergo until zootella.com's DNS is set. Fuji, at ../fuji, is the first user; fromergo.hide.md in its root is ergo's letter to it.
- Source material is ../cold3/icarus/core.js, which imports its test harness and guards from ../cold3/icarus/level0.js. icarus is a mine, not a museum: ergo takes the gems from both, function by function, and leaves the rough and early parts behind, including toss and TossError. A helper that comes over brings its words with it, essays, jokes, and emoji included, since cold3 will later delete its copy; quad-style.md's last section has the steps.
- The protocol's canonical function names are the JavaScript edition's; each edition spells them its own way, like `saySize4`, `say_size4`, `say_size4`, `SaySize4`, and `Size.kb`, `Size.KB`, `size::KB`, `ergo.KB`. A constant is a function with no arguments, and a dotted name reaches into a namespace of them. Adding a function means a vector file, four implementations, and a line in each of the four dispatch tables.
