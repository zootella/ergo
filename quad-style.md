# quad style

This is the style guide for writing ergo — the user telling you how to write it, in all four of its languages. It governs your choices about coding, commenting, documenting, and refactoring in JavaScript, Python, Rust, and Go. Your default modern style in each is already good; this document is the delta: where we deliberately differ from prevailing practice, and why. Where it's silent, good current practice in that language applies.

It's built on the JavaScript style guide of the application ergo grew out of, and its values are that guide's, unchanged. What's new is the line between style and format, drawn for four languages at once. Style is how code is structured, named, commented, and factored, and how it handles errors and trust; that's this guide, and it governs every edition. Format is whitespace, quotes, semicolons, and line breaks; that's each language's standard formatter, and it governs its own edition. Between the two sit the things a language has a settled convention about — the case of a name, the shape of a doc comment, the way a program fails — and there the language wins too. Picture one author writing fluently in four languages, not one text run through a translator: the meaning and the character are the same in every edition, and the idiom is whatever a native would write. The test is four mid-career engineers, each with years in one of the four languages: each opens their edition, runs the linter they always run, and finds nothing foreign. concept.md has the argument behind this, and construction.md the tooling.

By code we mean code and comments as one integrated system. The runtime reads only the code; every other reader reads the two as a single text. That's always been true for humans, and now it's true for agents: drop a capable agent into a repo with the comments stripped out, and its results suffer, because the comments carry invaluable context and meaning. The aim everywhere: code that runs reliably, is factored efficiently, and reads lyrically, for humans and agents alike.

Two ideas underneath everything here. First, **simplicity**: we write simple, modern code — each current language, used plainly. Not bleeding-edge syntax that shows off, and not the naive patterns of a first tutorial either: simplicity within what's modern and current. Python states simplicity as a core value — simple is better than complex — and every edition holds the same. Reach for the plain pattern over the fancy one, and when code grows complicated, break it into smaller, plainer parts rather than adding cleverness. Second, **attention**: a reader's attention is what every choice here spends or serves. That's not a rule about writing less — comments enjoy a huge budget in this style; by weight they often rival the code! It's a rule about balance: say the right amount in the right places, so understanding arrives as quickly and accurately as possible.

This document positions itself on the map of styles you already know — your own house style, each ecosystem's canon from PEP 8 and Effective Go to the Rust API Guidelines, the Airbnb style guide taught in bootcamps, the formatters and linter defaults, Clean Code and The Good Parts. We take the best ideas from these schools, but where we oppose one, the opposition is deliberate, and argued here with reasons. Knowing what the mainstream does, and choosing with intent, is part of understanding this style.

## Format

Format belongs to each language's standard formatter, run on save and checked in CI: Prettier for JavaScript, Ruff for Python, rustfmt for Rust, and gofmt for Go. Prettier carries two settings, `semi: false` and `singleQuote: true`, the configuration Vite and Vitest use for their own code; the other three run as they ship. Linters run with each ecosystem's recommended rules and nothing more: ESLint's `recommended`, Ruff's defaults, Clippy, and `go vet`.

That guide bans formatters, and its reasons are real: a tool that owns the whitespace erases the vertical alignment we write into it, and wrapping to a column turns a one-word change into a multi-line diff. ergo pays that price on purpose, for editions that each look the way their ecosystem expects. So give the formatter indentation, line width, line breaks, quote style, and spacing, and never hand-format around it. Where alignment genuinely carries information — a table of values, an alphabet with a row of carets beneath it — each formatter has a recognized escape for one block, `// prettier-ignore`, `# fmt: off` and `# fmt: on`, and `#[rustfmt::skip]`, while gofmt aligns neighboring trailing comments on its own. Use an escape rarely, so it reads as the signal it is: this whitespace is information.

A formatter decides much, but not everything, and what it permits without imposing is still ours. These parts of that guide's layout survive:

- Write comments in conversational lowercase, in every edition, for the same reason syntax highlighting paints them dim gray: to let the code, and its capitalization, stand out. Two forms are written in normal English prose, capitals and periods: the essay, and the doc comments that Python, Rust, and Go read out of the source. Both are described with the other comment forms below.
- Write comments in the active voice, and reach for the imperative when the comment says what the line does: _check m too_, not _m is checked too_. The passive costs a word and drops the actor, which is usually the very thing the reader came for — and once the actor is missing it's easy to leave out why, too. This holds in essays as well: _this check turns it away_ rather than _it is turned away_.
- Quote with double quotes inside comments and prose, in every edition. In JavaScript code, use single quotes for strings and backticks when interpolating, which Prettier's settings keep; the other three quote the way their languages and formatters do.
- In JavaScript, omit semicolons: `semi: false` removes them and adds back only the rare one execution needs. That guide's exception, two statements sharing a line because they're one thought, gives way, since Prettier puts each statement on its own line.
- In JavaScript, write a short `if` on one line without braces: `if (!row) return false`. A guard and its action on one line is a single readable sentence, and Prettier leaves it that way. The braced form holding two statements doesn't survive, and neither does the one-line guard in the other three languages, whose formatters open every block onto lines.
- Prefer `if` statements over ternaries. Let a ternary survive only when it's flat and simple, picking between two values — never nested, never carrying logic. Python's conditional expression and Rust's `if` used as a value answer to the same rule; Go has no ternary to tempt anyone.

The rest of that guide's layout gives way: tabs, except in Go, where gofmt uses them; unwrapped lines, except in Go, which never wraps; alignment by hand; and its spacing inside braces and object literals.

One thing about width is worth knowing in advance. Prettier, rustfmt, and gofmt leave a comment at the end of a line where it is, and don't count it against the line's width, so line comments stay as plentiful as this style wants. Ruff counts it. When a comment carries its line past 88 columns, Ruff breaks the code apart to make room:

	parts = s.split(
	    "."
	)  # the year, month, and day; then the clock; then the milliseconds into the minute

That's worse than either honest choice. In Python, when a line comment won't fit within 88 columns, put it on the line above, as a group comment for a group of one; when it fits, keep it on its line. Here the formatter bends a comment rule, and the formatter wins.

## Names

- Name things with complete, speakable words. **No abbreviations** — _configuration_ and _c_ are acceptable, _cfg_ is not. Treat an abbreviation that's a proper name out in the world, like HTML or URL, as a word: _someUrl_, _someHtml_, _someId_ — except in Go, which capitalizes an initialism whole, so _ISOToTick_ where the others say _isoToTick_.
- Name functions _verbNoun_, like _validateEmail_ and _parseHeader_; name getters as bare nouns. The words are the same in every edition, and only the case changes: _validate_email_ in Python and Rust, _ValidateEmail_ in Go. The protocol's canonical names are the JavaScript edition's, and construction.md has the table of spellings.
- Treat a verb prefix as a promise: if `is`* functions answer yes-or-no, every `is`* function answers yes-or-no. A reader who has learned one member of a family has learned them all, so never break a prefix's contract. The promise holds across editions too: in a guard pair, like _hasText_ and _checkText_, the _has_ asks and never fails in all four languages, and the _check_ enforces in all four. That's a promise about the pair, not about every name that starts with _has_: a method that asks about what an object holds, like an outline's _has_, still refuses an argument that's malformed, the way any function refuses a caller's bug.
- When a family of functions shares a domain, lead their names with the shared noun so they sort and read together: _credentialOauthSet_, _credentialOauthGet_, _credentialOauthRemove_.
- Mark a private helper — a function serving a nearby one — the way its language marks private: a leading underscore in JavaScript and Python, no `pub` in Rust, a lowercase first letter in Go. Never a leading underscore in Rust, where it means a name is deliberately unused and silences the warning that would say otherwise, nor in Go, where it's foreign.
- Use single-character names in exactly two places. First, conventional carriers a codebase establishes for itself — picture a project where every validation function returns a result object the code always calls _v_; after you've met _v_ twice, it never needs introducing again. Second, short-lived locals whose whole life fits on a screen — introduce these with a comment; the comment is the real description, and a long name would be a worse, endlessly repeated version of it. Prevailing style would lengthen the name until it describes itself; ours goes the other way: name it briefly, describe it richly, once, in the comment where it's born. A name is repeated at every use; a description shouldn't be. Of the four ecosystems, Go's culture is the one that already agrees.
- Follow the environment's case: `kebab-case` in CSS, `snake_case` in SQL (our_tables have column_names), and in code, the language's own: `camelCase` in JavaScript; `snake_case` functions, `UPPER_CASE` constants, and `CapWords` types in Python and Rust; `MixedCaps` in Go, capitalized to export. The words in a name are style, and every edition shares them; the case is format. In JavaScript, write **no ALL_CAPITALS** — those read as a shout and are clumsy to type — so where you'd normally use SCREAMING_SNAKE on a constant, write `const camelCase` at the top of the file instead, like `Size.kb` and `Time.hour`. That's a house choice within what JavaScript allows, and it stays in JavaScript: PEP 8 asks for capitals on a constant and Rust's compiler warns without them, so `Size.KB` and `size::KB` keep the deeper rule, follow the environment's case, rather than break it.

The rules in this guide have exceptions — you'll meet them in existing code, and sometimes the right move is to write one. Is _maximum_ really required instead of just _max_? No: _max_ and _min_ are words programmers speak, and the rule against abbreviations was never against words. Decide cases like this by returning to what the rule protects — quick, accurate understanding — and choosing what serves it. Almost always that's the rule as written; occasionally it's a small, obvious exception, taken without ceremony; and when a case genuinely pulls both ways and the stakes are real, ask the user. Never follow a rule into code you know is worse, and never queue up permission requests for calls you can make — both mistake what this document is: values first, with rules as their everyday form.

## Comments

The signature of this style is comment density: get ready to comment far more than you normally would, and differently. This is a considered rejection of an orthodoxy you've absorbed. _Clean Code_ taught that a comment is a failure to express yourself in code, and a generation of review culture inherited the reflex — comments as apologies, deleted on sight, replaced by ever-longer names and ever-smaller functions. We hold with the older and better school — Knuth called it _literate programming_, a program written for people and only incidentally for the machine: prose carries intent, context, and caution that code cannot, and refusing that channel throws away half the bandwidth of the file. Write toward this bar: comments so complete that given only a function's name, parameters, and comments — body stripped away — a capable engineer or model could write a functional equivalent.

Put the comment at the end of the line it's about:

	let a = [] //the array we'll fill with results, sort, and return

In JavaScript, leave no space after the slashes; Prettier sets one before them. Python, Rust, and Go write the marker the way all their readers expect, with a space after it, `# like this` and `// like this`, and Ruff sets two spaces before a `#`.

Write it lowercase, with no closing period. Separate two clauses with a semicolon:

	//the address is gmail; apply the extra normalization rules

Let several sentences form a short paragraph — capitals and periods between sentences, but the same lowercase open and bare end:

	//the first note. And a second, a clarification. Perhaps a third situation to describe, as well

Comments come in four sizes, small to large: on the end of a line; introducing a group of lines; above a function; and the essay.

The first two live inside function bodies. Put line comments to the right of code, not above, so comments stay plentiful without lengthening the file. Split a longer function into conceptual groups with blank lines; the reader sees two groups and knows the function works in two parts, then scans deeper to learn what each part is. Put a single-line comment above a group when it speaks at the group's altitude — what these lines accomplish together. Put a comment about one line on that line.

Above a function, write the same style one step zoomed out: what this is for, plus anything clever, unique, or tricky. Javadoc-style blocks are the anti-pattern — formulaic and pedantic, covering the trivial and the tricky at equal weight until the important part is lost in the average, sitting atop code the reader still has to figure out. Comment instead like the engineer who knows this area talking to a capable newcomer, saying: _here's what you actually need to know_.

In JavaScript, that comment is a lowercase line comment like any other. Python, Rust, and Go each read the comment above a function out of the source and show it somewhere else — in help() and an editor's hover, on docs.rs, on pkg.go.dev — so there it takes the language's doc comment form, written in sentences with capitals and periods, since it will be read as prose away from the code:

- Python: a docstring on every function and class, a sentence or two in triple double quotes.
- Rust: a `///` comment on every item, public or private. It's markdown, and an example in it compiles and runs as a test. A function that can panic says when, under a `# Panics` heading.
- Go: on anything exported, a doc comment that starts with the name, like _SaySize4 says a count of bytes…_, in full sentences. On anything unexported, the house lowercase line, still starting with a function's name.

What a doc comment says stays ours: the need the function serves and what's tricky about it, never a block of parameters and returns. Rust's `# Panics` heading and Go's name first are the only structure, because they're what those readers look for.

Fourth, the essay. Write one when a larger system needs explaining at a larger level — an overall design, a novel mechanism running full stack, choices and their reasons. The comment grows into a `/* */` block in JavaScript, and into paragraphs of line comments in the other three, which is how Python, Rust, and Go write a long comment, with a bare `#` or `//` between paragraphs. Either way it switches to normal English prose, capitals and all. Write it like a little document, but keep it with the code, at the best place it can sit, and keep it a half screenful, not pages. The essay speaks from ten thousand feet, and it's the one place comments are allowed to remember — the history, how we got here, the alternatives weighed and set aside. Essays span larger time and space; keep every smaller comment tight to here and now.

A long file marks its chapters with a heading where each region begins: a figlet banner in JavaScript, and a bare lowercase line like `# tick` or `// tick` in Python and Rust. In Go, a heading needs a blank line below it, or it becomes the doc comment of the declaration beneath.

Never restate the line. Positioned at the line, a comment never has to explain where it applies — the reader is already there — so spend all its words on what that line is doing in service of the surrounding task. Writing good comments means balancing three tensions, deliberately:

**Comment, or let code stand alone.** The test is whether the comment speeds understanding: would a reader move through this stretch faster, easier, and more accurately with it than without it? Trivial code commented is clutter — it slows the eye and dilutes the comments that matter. But an unfamiliar pattern uncommented is worse: every future reader stops to reverse-engineer what one sentence would have handed them, and a reader who half-remembers the pattern loses the cheap reinforcement of reading the comment, seeing the code, and having their understanding confirmed. Aim for neither warning signs everywhere nor minimalism — say the right amount in the right places, tuned for maximum swiftness of understanding. Done well, the presence of a comment itself carries information: something here deserves a moment of your attention, and these words exist to make that moment short.

**How versus why.** This tension is about which kind of information a comment carries. If code is genuinely difficult to follow, don't reach for a comment first — rewrite toward code that doesn't need one! Sometimes the difficult form really is right: a recent language feature, a terse chain that's the clearest honest expression, a spot with a genuine pitfall — an exception that won't surface visibly from inside a functional chain. Keep those, and comment the mechanics and the trap: that's _how_ work, and keep it light. Spend most comments on _why_ work, the mission the comments signed up for: what this line contributes to the task around it, what constraint from elsewhere lands here. And the _why_ is always today's _why_: describe what the code does and is for right now, never its history and seldom the alternatives it beat — that remembering belongs in an essay.

**Altitude.** This tension is about the height a comment speaks from. Every comment has one — this line, this group, this function, this system — and the failures sit at the extremes. Too low, and it restates the syntax the reader just parsed for themselves. Too high, and a line comment strains to narrate system design: verbose, brittle, and quietly wrong after the next refactor, because nothing nearby will remind anyone to update it. Match the comment's height to its place. Speak a line comment to its neighborhood — this line, in service of this part of this function. Have a function comment tell what the function is good for — the need it serves, which is nearly but not quite the story of its callers: describe the need, not the call sites, and the comment survives when the callers change. And when the information is genuinely system-height, don't crush it into a line comment — that's the essay's job.

Comment what's different, not what repeats: in a family of similar functions, comment the first thoroughly — introduce the shared structure there — then comment later members where they diverge, and why. Do the same for a fancy pattern or unusual platform object used in many places: one full explanation where it lives or first appears, and usage comments that just note it's in play. But mind the radius: an introduction only serves the reader if it's where they'll actually be. A reader lands directly in one function and reads its screenful, its section, its family — not a different chapter three screenfuls up. When a pattern resurfaces beyond that natural viewport, add a one-line reintroduction at the new site — it costs almost nothing; the reader who needed it saves minutes, and the reader who didn't skips a line.

Say the same thing in all four editions. A function's comment carries the same sentence in each, an essay is the same essay in each, and a line comment on the same step of the same algorithm says the same thing in each, changing only where the language really does differ: one edition raises where another panics, or a u64 can't reach a value that Python's unbounded int can. Then a reader who knows one edition finds their place in another by its comments, and a difference between two editions' comments marks a real difference between the editions. When you change a comment in one edition, change it in all four. It's also what will let one small extractor build a reference page from all four editions' comments, as concept.md describes.

Welcome honest temporary comments — real work-state lives in the code. The strongest form is the `ttd` note (things to do): `//ttd march, unify these two paths after the migration`. The token is invented on purpose: it greps clean with no false positives, types without caps lock, unlike TODO, and reads the same after any language's comment marker. The month is a timestamp — bare month for this year, month and year like `ttd march2025` for notes surviving from earlier — marking when the issue was raised or last visited. And ttd notes carry special rules: **only the user adds, rewords, or removes them.** A single terse `ttd` can carry weight across sprints and epics — a business concern, a security follow-up, a half-finished design. Move one intact while restructuring, write around one, but never edit or delete one — even when deleting the code around it: the structure washes away and the `ttd` comments remain, sitting on the dry riverbed where they landed. If one is in the way, stop and ask; the user will make the edit or give exact instructions permitting it.

Existing code may use emoji sparingly, as landmarks — a marker that makes a section or an essay findable at a glance. Where a file already uses an emoji pattern, like bulleted step markers or warning marks, maintain it; where emoji appear as accents or fun, leave them be — and don't introduce new decorative ones of your own.

Finally: comments and names are code, and readability is a deliverable. The human path to this quality runs through iteration — finish the logic, pass the tests, then reread as a stranger, renaming and recommenting until understanding comes quickly. You don't need the lengthy process to reach the outcome: write it that way in the first draft. Then still take the stranger's read before calling the work done — the next reader lands on this code cold, and the standing question is: _Could this be any easier to quickly and accurately understand?_

## Reserved signals

Two places we invert prevailing JavaScript style, both for the same reason: when the strict form is rare, its appearance carries information.

- Default to `let`, even for bindings that happen never to change. Reserve `const` to draw attention on purpose: this reference should never change, or must never change — factory presets, imports, module-level singletons. This inverts prevailing style, which writes `const` everywhere and downgrades to `let` only where reassignment forces it; that habit isn't actually safer or more readable — reassignment bugs are rare, and `const` leaves the object behind the reference fully mutable.
- **Never return mixed types to carry extra information.** With returns in one shape, and the guards below checking inputs, types are already certain wherever values meet — so default to `==` and `!=`; coercion has nothing to bite. Reserve `===` and `!==` for the rare genuine exception — a null-versus-falsy distinction, a mixed-type api you don't control — where the strict operator's rarity reads as a flag: _be careful right here_. Crockford's _Good Parts_ put `==` on its bad-parts list and every linter followed; that fear is valid where types are uncertain. Ours aren't.

Prevailing style uses `const` and `===` everywhere, which spends both signals down to zero.

These two are JavaScript's own grammar, and they stay in the JavaScript edition, where ESLint's recommended rules include neither `prefer-const` nor `eqeqeq`, so the linter leaves both alone. The value under them — keep the strict form rare, so its appearance carries information — holds everywhere, and the other three languages already express it in their own grammar. Rust makes every binding immutable by default and marks the exception, `let mut`, which is this very idea built into a language. Python and Go have no way to freeze an ordinary local and no loose equality to reserve the strict one against, so there's nothing to invert; write them the way they're written. And where JavaScript's `===` flags a genuine distinction, like `t === false` in a reader whose answer can be the tick zero, which is falsy, the other editions draw the distinction with types: `t is None` in Python, an Option in Rust, a second return in Go.

## Truthiness, text, and absence

- Don't overload falsy with meanings: write `if (o)`, and don't turn _undefined_, _null_, and _false_ into different messages. Where a value crosses a boundary, prefer text-or-blank over flavors of absence: a blank string simply means there's nothing, and no extra meanings ride on null versus undefined. Imagine the caller is going to test your return for falsiness, and that is all.
- Zero is a normal number. `if (count)` works, because zero is falsy — but write `if (count > 0)` anyway. The comparison tells the reader that count is a number being measured against a threshold; the bare truthiness test makes them stop and confirm this is the zero-is-falsy trick rather than a presence check. Keep truthiness shortcuts for presence, like `if (o)`; give numbers real comparisons.
- Blank is still text. A blank string is falsy, but blank is often a fine value — a successful fetch can return an empty body. So `if (s)` asks two questions at once: is there a string, and is it nonblank. Write code that asks the one question it means — a tiny guard of your own, like a hasText(s) that's true only for a string with more than whitespace in it. This is about asking clearly, not answering cleverly: never flip it around and make false, blank, and text three different messages from one return — that's exactly the falsy overloading banned above.
- Have get-style functions return the thing, or false when not-there is an ordinary answer. This isn't the mixed-type return banned above: false carries only absence, and the caller tests falsiness — that is all.

Those are JavaScript's mechanics, and the rules hold in each edition's own. Python has truthiness of its own, and the rules apply there as written, with None in place of false: zero is a number, so compare it; blank is still text, so ask about text with a guard; and a value that can be zero, like a tick, is tested `is None`, never `not t`. Rust and Go have no truthiness, so every question is asked explicitly, and each already has a form of absence that carries only absence: an Option in Rust, and in Go a second boolean return, the comma-ok form a map lookup uses. Those are what the thing-or-false rule becomes there.

## Exceptions

Where code fails loudly and where it works around trouble quietly is among the most consequential choices in an application's architecture. The rule: loud and brittle for programmer errors; resilient and forgiving for user input, network responses, and third parties. This section and the next are that rule made concrete.

Exceptions are truly exceptional — never an everyday tool, never control flow. Since the 1990s made _try/catch_ available, and thus fashionable, mainstream code has used exceptions as a second return channel, and paid for it: functions that communicate both by value and by throw, try blocks nested until the logic drifts far from the left margin, and every caller left guessing what might fly out of what. We intentionally left that school, and got simpler code with improved safety — fewer possible paths through the logic means fewer paths nobody reasoned about. _Go_ made the same bet at the language level — errors are values, returned and handled like anything else — and our result objects make it at the level of style.

Build the architecture as a walled city, with try/catch at exactly two gates:

At the bottom gates, where our code calls down into apis and modules we don't control, wrap the call in a tight try/catch that converts exception-speaking code into values. A third-party service throwing or returning 500 is a Tuesday, not a bug — catch it, pin the error into a result object, and let ordinary code decide what happens next: retry, route around, or report failure as a value.

At the top gates — every entrypoint where our code starts running for the framework or platform around it — write one broad catch: log anything that escaped, with full context so the team will see it, and fail the request loudly and visibly. An exception reaching this gate means a bug in our code, or input so malformed it suggests tampering; either way the remedy is report-and-fix, not smooth-over-and-retry. Wrap a standalone script the same way at its smallest: put the work in main() and catch once at the bottom — `main().catch(e => { console.error(e); process.exit(1) })`.

Inside the city walls of the code we write and control, life is calm. Never throw for flow and never catch: no rethrowing, no try around code that merely "feels risky", no dual-channel functions that answer both by return and by throw. Let happy and sad paths near the user complete without an exception firing under the hood — wrong password, taken name, rate limited are ordinary answers; return them as result objects like `{success: false, outcome: 'WrongPassword.'}`, where the outcome is a short constant the caller can branch on and logs can show. The only deliberate throws inside the city come from guard checks (next section) announcing a bug in the code above — let those fly uncaught to the top gate, exactly as intended, because that's what they are: our mistake, to be fixed in code, not negotiated with at runtime.

What this buys: every function inside communicates one way, by return value, so control flow is visible on the page — reading a function, you can see every exit. Code stays near the left margin instead of nesting through pyramids of try blocks. And safety improves twice over — the top gate means nothing escapes unreported, and the simpler flow means fewer control-flow bugs to escape in the first place.

In ergo, each language's own mechanism plays each part, and there's no custom throw helper and no custom exception class in any edition:

- **A caller's bug** fails loudly, from a guard: a thrown Error in JavaScript, a raised ValueError or TypeError in Python, a panic in Rust and Go. It's meant to fly uncaught.
- **An ordinary answer** is a value. Rust and Go build this rule into the language: a Result or an error is the result object, returned and handled like anything else, and a panic is kept for a bug. So in those two, a reader handed text it can't read returns an Err or an error, the way `str::parse` and `strconv.Atoi` do. Python raises for that instead, because Python does, the way `int("x")` raises, and JavaScript throws for now; concept.md has that open question.
- **A bottom gate** catches tightly, where the platform speaks exceptions for an ordinary answer, and returns a value. Python's datetime raises for february 30, and the Python edition catches exactly that ValueError and answers None.
- **The top gate** is each driver's loop, the one broad catch that reports whatever escaped as the response and keeps serving: `try` and `catch` in JavaScript, `except Exception` in Python with a `# noqa` saying why the blind catch is right here, `catch_unwind` in Rust, and `recover` in Go. Nothing else in ergo catches broadly.

## Guards and trust

Check inputs at the top of important functions. A line of checks there is a gate that every call must pass through: any imaginable correct use passes untouched; a call that trips one has revealed a bug in the code above, caught at the boundary instead of corrupting quietly below. Make the check throw — that's the programmer-error loud path from the section above — and have it carry the named variables involved, so the mistake arrives in the log with its context. Write checks that encode _intent_, narrower than _mechanics_: a function might run fine on a blank string, but if callers should never pass blank, a check at the top catches the upstream bug the moment it happens, right where it happened. These are preconditions, enforced at runtime, where they hold against the actual data of this call, not just the declared shape of the code. In a young project, write them as plain lines — `if (typeof s != 'string' || !s.trim()) throw new Error('expected text: ' + s)` — and as the same checks repeat, promote them into the project's small guard family, keeping the prefix promises from the names section: has* and is* to ask, check* to enforce. Grow the family out of repetition; don't install it on day one.

In ergo the guard family is part of what ships, and it follows one rule: every kind of value a function refuses has a _has_ that asks and never fails, and a _check_ that enforces, like hasTick and checkTick before tickToIso. A caller holding a value from outside, like a system clock or a file's modified time, asks first, and once _has_ says yes, nothing in ergo fails on that value. That's one predicate per kind of value, not a checked twin of every function, so the family stays small as ergo grows. It matters most in Rust and Go, where a panic means a bug and can't be caught the way an exception can: a function that panics with no way to ask first would leave its caller unable to avoid one, and ergo never does that.

A guard checks what the language can't. In Rust and Go the signature already refuses text where a count goes, so a guard there checks intent, like a tick's range. JavaScript and Python let anything through a parameter — a type hint is a note to the reader, not a gate — so their _has_ functions check the type too, and in Python they remember that a bool is an int.

Put defense at trust boundaries, not everywhere. Checks, optional chaining, default arguments, and fallbacks are load-bearing where untrusted data enters — HTTP bodies, decrypted payloads, provider responses. Keep them out of trusted code, where they're noise: they hide where the real defense is and erode the very contracts the checks establish.

Never keep a part just because it was seen near working code. The header copied from a tutorial, the defensive check nobody can explain, the config flag that was in the example — these are parts wearing the form of working code without anyone having traced their function. Give every part a reason to be there, and when you're unsure whether a part is necessary, find out — read the documentation, read the code beneath, run a quick experiment in the environment where the behavior actually matters — rather than leaving it in just in case. This is what prevents the growing garbage patch of parts nobody dares remove.

Never polyfill, and never write code that checks whether the platform supports a feature — each edition targets its language's current release, which construction.md names, so the features are there; use them directly. The one exception is behavior that would fail silently: most mistakes announce themselves by throwing or visibly breaking, but a few — an encoding detail, a pasted constant — can be wrong and still run, quietly corrupting the data they touch. Pin behavior like that with a permanent test against known correct answers: feed in fixed inputs, expect the exact outputs the standard publishes. In ergo that's the shared vectors, and where an edition carries a piece of the platform itself, like the Rust edition's calendar arithmetic, the cross-edition fuzz test measures it against the other three platforms on random values. Trust the platform for everything else.

Log freely while building something — that's part of watching a pattern come alive — and remove those logs once it's confirmed working. Treat permanent logs differently: they're not print statements but records of system behavior. Place them where things could go wrong, or where a rare, important pathway runs, so that when something does go wrong, there's a chance of seeing it later.

## Factoring

The guide this one grew from asks an application to use the minimum of its framework and keep its logic away from it: thin framework files calling down into plain modules, so the logic survives when the framework changes and only the thin layer is rewritten. ergo is where that factoring arrives — plain modules taken out of an application and made to stand alone — so it holds itself to the far end of the rule: no framework, and the platform before anything else. And it takes isomorphism a step further. Where an application runs one validateEmail on the page and on the server, ergo runs the same function in four languages, giving the same answers, so a Rust backend and a JavaScript page agree.

- Use the platform, and take from a library only what the platform can't do. Judge it function by function and form by form, not family by family: JavaScript's Web Crypto hashes SHA-1 and SHA-256 all at once, at native speed, so ergo's sha1 and sha256 are Web Crypto, and noble comes in only for what Web Crypto lacks, the hashers that take a piece at a time and BLAKE3. A library already in the dependencies is never a reason to use it for more. Once one is there, the pull is to route everything through it, and that trades the platform's speed, and the scrutiny the platform already gets, for a second copy of something the platform does well. Where the platform does fall short, the library has to meet concept.md's bar: one experienced engineers in that ecosystem already trust, and in JavaScript, plain JavaScript that runs in a page and a web worker.
- Build ergo from ergo, and use its helpers early and often. ergo exists to make other code shorter and plainer, so its own code is the first place that promise is kept: wherever one of its helpers, or a chain of its methods, makes a stretch shorter and plainer, reach for it, even when the helper is only a thin wrap around a platform or library call, and even in the harness and the tests. Where one wouldn't make a stretch plainer, leave it out: ergo uses ergo where it helps, not everywhere it could, and a shorter call stack is sometimes the plainer answer, the way sayTimeRace pads its own numbers rather than reading the rest of a minute as a tick to borrow sayTick's padding. `(await sha256(Data({ text: s }))).base32()` is the shape to aim for: each step one plain call, and the line reading the way you'd say it. Each such call lives in exactly one helper, and everything else goes through it, the way a project using ergo would. That keeps each decision about the platform in one place: moving sha256 from noble to Web Crypto rewrote one function, and its callers only had to await it. And it makes ergo the first and most thorough user of every helper, so an awkward one is felt here before anyone else feels it. So the drivers read tagged bytes through Data's own base16 reader, base62's decoder assembles its bytes in a Bin, and when the fuji hashes came over from the original, they were built from ergo's own Data, Bin, sha256, and Size constants, never from Web Crypto, noble, or hashlib directly.
- Make the hard core of a difficult thing a pure function, wrapped by a thin function that does the platform and storage work. Pure cores are trivially testable, and in ergo they're also cheap to specify: a pure function takes a vector, data in JSON that all four editions run natively, while anything with state needs a script and four drivers. Ask of each new helper whether its hard core can be a pure function with a vector.
- Take bytes that arrive over time with an object you feed, and wrap the language's streams around it. Make it with what it needs up front, `update` it with each piece in order, and `digest` for the answer, the words a hasher already speaks, so it works wherever bytes come from: an upload's chunks, a Node stream, a loop over a file. A thin wrapper reads a stream into it and holds the progress callback and the cancelling; `update` never fails, and a fact about the bytes, like too many or too few, comes back from `digest`. `FujiHasher` under `hashStream` is the example, and concept.md has the reasoning.
- Choose plain data over classes. In JavaScript, build `let o = {}`, fill it in the lines that follow, and write families of functions that operate on the shared shape; in Python, write functions on plain data, with a class only as a namespace, like Size; in Rust and Go, write a struct and functions on it. Related: when a function takes several parameters, pass them by name — one object in JavaScript, keyword arguments in Python, a struct in Rust and Go — self-labeling at the call site, immune to ordering mistakes, easy to extend.
- When a JavaScript object has to keep private state behind methods, like Data, write a class with private fields, and keep the class private behind a plain capitalized function that calls `new` for the caller: `export function Data(p) { return new _Data(p) }`. The class is the platform's own way to give every object one shared set of methods while keeping what each one holds truly private. Without one, you get one or the other: an object made inside a function keeps its members private, but carries its own copy of every method, which made each Data about ten times the size it is as a class, while an object over one shared set of methods leaves its members where any caller can reach them. The function in front breaks with convention on purpose, so `new` appears once inside ergo and never in a caller's code, and making a Data reads like making anything else in ergo: `Data({ text: s })` beside `Tag()` and `Bin(n)`. Call a method on its object, like `d.base16()`, since a method taken off its object has nothing to work on. Don't give the class the exported name, either: inside a class named Data, the word Data means the class, so each `Data({ array })` in its own methods would call the class without `new`, and throw.
- Prefer fewer, longer files, with region comments as chapter headings. Each edition's library is one long file — ergo.js, `__init__.py`, lib.rs, and ergo.go — and a family of functions is a region in it, under its essay. Where an ecosystem requires its own structure, like Python's `src/zootella/ergo/`, Rust's `src/bin/` for a binary, or Go's `internal/` and `cmd/`, comply, and keep those required files thin, calling down into the long one. The payoff: code that changes together lives together, so adding a function touches one vector file, the long file in each edition, and a line in each dispatch table, not twenty files.
- Refactor together, and completely: when usage shifts or a better pattern emerges, confer scope with the user, then rename and move immediately so the whole codebase reflects present understanding. Half-refactored artifacts and vestigial layers make appearances impossible to trust. And when a cleanup fixes an anti-pattern in one spot, sweep the neighbors for the same pattern before calling it done. In ergo, together means all four editions at once: a rename, a changed answer, or a reworded comment lands in every edition, with the vectors, the dispatch tables, and the site, so the editions never disagree about what they are. The shared suite catches a behavior that moved in only one edition; nothing catches a comment that did, except you.

## Bringing in the original

This last section is less style than procedure, for the stretch ahead. ergo's adolescence is the move of helpers and their tests out of the original: the file of JavaScript helpers in icarus, with the most years of use behind it, in the application ergo grew out of, along with the pieces of the guard and test layer they lean on. The original is never edited; ergo takes from it. A helper comes over in two phases, JavaScript first and the other three editions after, which CLAUDE.md lays out, and these steps hold in both. Later, the application will import those helpers from ergo and delete their first expressions from the original. So once a helper has moved, ergo is the only place its words live. The tests check that the code came over right. Nothing checks the words: an essay left behind, the reason for a choice dropped as clutter, a joke smoothed into a neutral sentence, an emoji that marked the cool part — each is lost for good the day the application deletes its copy.

The original is a mine, not a museum, and that's about what comes: a function arrives because it earned its place, and the rough and early parts stay behind, the original's own throw helper and exception class among them. But a function that earns its place arrives whole. Its comments are part of the gem, not the ore around it: the design and the reasons for it, the history in an essay, the _hey, reader, check out this part_, and the winks and jokes that make a reader glad they kept reading. Carry them all.

1. **Read the whole neighborhood first, then choose what comes.** Before writing anything, read the helper, its family, the essay above it, the tests below it, and whatever it leans on in the guard and test layer. Then choose by two tests. A close-knit family comes whole, its members built on each other or meant to be used together, even when only some of them are needed now. Anything else comes only when something in ergo needs it. Sitting in the same region of the original isn't a reason, and neither is being small and useful. Name what needs each arrival before it comes.
2. **Inventory every comment**: essays, line comments, group comments, the comments inside the tests, diagrams, emoji, asides, jokes. Each one gets a destination in ergo, or a reason it stays behind.
3. **Carry each to its place.**
   - An essay comes over as an essay, under its family's heading, in all four editions. It keeps its history, since the essay is the one comment allowed to remember.
   - A line comment stays on its line, in every edition, through the comment forms above.
   - A comment in a test goes with the case it describes: into the `note` of the vector that pins that case, the way the original's "mid afternoon on leap day 2000" did, or, when it teaches how to use the function, into the example the site shows.
   - A diagram keeps its alignment, behind the formatter's escape for one block, like the row of carets under base62's alphabet.
   - Emoji come over where they sat, in all four editions. The rule against new decorative emoji is about ones you would add; these are the author's, and they move like any other word of a comment.
   - A joke or a wink comes over in all four editions. One that only lands in JavaScript stays in the JavaScript edition.
4. **Change form, never voice.** A comment changes only where it has to: each language's marker, case, and doc comment form; a mention of the original's throw helper, of a helper from its guard layer that ergo doesn't have, or of the application's machinery, like a fuzz loop switched off in the code, which becomes ergo's own, like `ERGO_FUZZ`; the name of the application, or of any project downstream of ergo, which becomes a general phrase, like the application or an app built on ergo, since a reader who starts from ergo can't place it, while icarus, the upstream, keeps its name; and any fact ergo's version changed, since every comment stays true to the code it sits on. Fix a typo. Leave the rest as it was written. A wink rewritten into a neutral sentence hasn't been improved; it's been lost.
5. **Leave ttd notes where they are.** Copying a ttd note into ergo would be adding one, and only the user adds them. Name each one you pass, and the user decides whether it comes.
6. **Account for every comment.** Before calling it done, read the original beside the four editions, and account for each comment: carried, changed for a reason, or left behind with the code it described. The only comment left behind should be one whose code didn't come either.
7. **Record what changed.** Each way ergo's version answers, refuses, or is named differently from icarus's, and each helper in the family left behind, goes in icarus-migration.md, checked against icarus's own code, by running it where you can. Keep it out of the comments, essays, and docs, which describe ergo as it is: a reader new to ergo needs to know a Data can be empty, not where icarus's couldn't be. The essay still remembers ergo's own history, how a design came to be; what a project moving from icarus has to change belongs to the migration.
